# MooKKo 담당 공통 규칙

## 일하는 방식
- 각 담당은 Claude 앱 세션 하나입니다(사용자 2026-11-03, AI 매니저·하네스 서버는 쓰지 않음). 일감은 PM과 다른 담당의 세션 메시지로 받고, 결과도 메시지로 보냅니다(요청한 담당·통합 담당·QA). 담당과 세션 이름은 하네스 `config/roles.json`, 경로 주인은 제품 `docs/coordination/owners.json`입니다.
- 범위 밖 일이 필요하면 그 담당이나 PM에게 메시지로 요청합니다. 요청은 편집 허가가 아닙니다.
- 사용자 결정이 필요한 일(범위, 우선순위, 비용, 보안 예외, 언어·런타임, 돈 정책)은 임의로 정하지 않고 PM에게 올립니다. PM은 사용자 권한을 대행하고 (사용자 2026-10-31), 결정마다 날짜와 사용자 원문을 붙여 전합니다.
- 하루 마무리(18:30 지시)에는 그날 세션요약 파일(`일일보고서/<날짜>/세션요약/<담당>.md`: 완료·진행 중·남은 일·막힌 것)을 씁니다.
- 사용자에게 승인·확인을 묻지 않습니다. 스스로 판단할 수 있는 일은 근거를 남기고 진행합니다.

## 기준
- 기준은 "가장 높은 수준"입니다(사용자 2026-10-20: 알리페이·알리바바급 속도·보안·안전, 99.99%). 낮은 목표를 임의로 두지 않습니다.
- 개인 운영이라 운영비가 낮아야 합니다. 메모리·프로세스 수·외부 서비스 비용을 늘리는 설계는 근거를 적습니다.

## 코드 (정본: MooKKo `AGENTS.md`, 관문: `docs/policy/gates.md`)
- 서버 실행 코드는 Rust만 씁니다. 모든 crate 루트에 `#![forbid(unsafe_code)]`. Python·PowerShell은 CI·시험·개발 도구에만.
- 커밋 전에 Linux에서 제품의 `scripts/ci/check-all.sh`를 실제로 돌리고 명령·종료 코드·결과를 보고합니다. 검사 본체는 하네스(MooKKoHarness)의 `ci/check-all.sh`이고, 제품 `harness.lock`에 고정한 판이 돕니다. 내부 시험 서버가 생기기 전까지는 WSL 배포판 `MooKKo-Linux`에서, 빌드 자리(`config/dev/build-slots.json`)를 거쳐서만 돌립니다. Linux 밖에서 돌린 결과는 통과로 세지 않습니다. 통합 담당이 같은 검사를 통합 판에서 다시 돌리고 그 결과만 믿습니다.

## 정해진 방식 (사용자 결정, 어기면 하네스가 반영하지 않음)
- 언어별 코딩 규약(정본은 하네스 `policy/conventions/`, 제품 `docs/policy/conventions/`는 고정 판의 사본: Rust·프론트엔드·SQL·Protobuf·도구)을 지킵니다. 코드를 쓰기 전에 그 언어 스킬(정본 하네스 `skills/`, 제품 사본 `.claude/skills/mookko-<언어>/SKILL.md`)을 읽습니다. 규칙 끄기(`#[allow]`·`eslint-disable` 등)는 예외 등록부에 없으면 반영되지 않습니다. QA는 관문 CONV-01로 규칙 번호마다 판정합니다.
- 모든 앱은 공용 서버 엔진 하나를 씁니다. 서비스 crate는 엔진 포트만 쓰고, HTTP 서버·HTTP 클라이언트·DB 드라이버·gRPC·캐시 클라이언트 crate를 직접 쓰지 않습니다. 엔진에 없는 기능은 바탕(foundation) 담당에게 요청합니다.
- 전부 모듈화: 바깥 시스템은 엔진 포트 + 어댑터 crate + 적합성 시험으로만 붙입니다.
- 포트·주소(IP·호스트·URL·host:port)는 코드·상수에 두지 않고 JSON 설정에서만 읽습니다. 시험도 fixtures JSON에서 읽습니다.
- 웹 화면은 `web/`(pnpm)에서 React + TypeScript + Tailwind CSS만 씁니다. 내부 화면은 Vite SPA(엔진이 정적 파일 서빙), Next.js는 공개 SEO 화면 앱에서만. API 클라이언트는 `.proto`에서 생성한 것만 씁니다.
- 이름에 Rust를 붙이지 않습니다(MooKKo, `mookko-*`).
- 자기 담당 경로(owns)만 고칩니다. 커밋 전에 `git diff --cached --name-only`로 확인합니다.
- C# 판은 없어졌습니다(사용자 결정 2026-10-29 참고만·삭제 예정, 2026-10-30 C# 하네스 철거). 명세 근거로 예전에 적은 C# 사본 경로:줄은 관문 SPEC-01이 정한 대로만 읽고, 실행·시험·통과 기준으로 쓰지 않습니다. 새 기능은 새로 설계하고 근거 문서를 적습니다.

## git
- 커밋 첫 줄 `[영역] 한 일`, 본문에 무엇을 왜 했고 어떻게 확인했는지. 본문 끝에 `작업자: <엔진>`(당분간 `작업자: Claude Code`만, 사용자 2026-10-29)과 그 세션 모델의 Co-Authored-By 줄. 모든 세션이 같은 git 사용자라 작성자로 담당을 가릴 수 없으므로, 담당은 브랜치(`claude/<이름>`)와 owners.json으로 가립니다(보안 파일은 하네스 `check-owner-paths.py`).
- 자기 worktree(`.claude/worktrees/<이름>`)와 브랜치(`claude/<이름>`)에서만 일하고, push는 자기 브랜치만 합니다. `main`·`foundation/engine`에는 push하지 않습니다. 통합 담당(RustDev)만 check-all을 통과한 통합 판을 `foundation/engine`에 넣고 같은 커밋을 `main`에 fast-forward로 올립니다(사용자 2026-11-03). reset·rebase·태그·남의 브랜치 이동을 하지 않습니다.
- 다른 담당에게 파일을 넘길 때는 자기 owns 경로에 커밋하고 커밋 SHA와 저장소 안 경로를 적습니다.

## 보고
- 한 일, 바꾼 파일, 실행한 검증(명령과 결과), 남은 일을 적습니다.
- 실행하지 않은 검증을 통과로 쓰지 않습니다. 문서 작성, 담당 등록, 시험 개수만으로 기능 완료를 주장하지 않습니다.
- 개발이 끝난 커밋은 push한 뒤 통합 담당에게 커밋 해시와 check-all 결과를 보내 통합을 요청합니다. QA 판정은 통합 담당이 통합한 판으로 분야별 QA 세션(qa-design·qa-engine·qa-services·rust-qa)에 요청합니다. 판정 세션은 개발과 다른 모델을 쓰고, 결과마다 엔진(모델 id)을 적습니다.
